# Employee model crate

The employee model (training card values, projection, careers, planner, product switching) as one Rust crate built to WebAssembly: the only implementation. It replaced the JS model.

The JS files that keep the old API names (`EmployeeCore`, `EmployeePlanner`, `EmployeeCareer`) are the module's JS API, and they stay: besides display text (trait names, notes, check messages, plan descriptions) they free the module's handles (`EmployeeCore.subject`, the planner's snapshots and sessions), run long work in steps so the page keeps progress and cancel (`EmployeeCareer.run`, `recommend`'s rounds, the keep session's `prepare`), and shape inputs (card pricing's subject over its options, the career's company, the regional bonus) and results (the employee after an outcome, the output-only plan). The UI and the tests call them. They hold no rules. Tables and calls that need no shaping are the module's own: `EmployeeModel.CFG`, `NUMERIC_CARDS`, `CHURN`, `TOOL_TYPES`, `SPECIALIZATION`, `CHANGE_ITEM_COST`, `SPIKE_RATIO`, `MAX_REROLLS` and `EmployeeModel.api.*` (`careerMerge`, `careerCompare`, …), which the UI uses directly. A change to a rule goes in here, never in those files.

## Toolchain

- **Rust:** stable, pinned in `rust-toolchain.toml` to `1.99.1`. rustup installs it, with the `wasm32-unknown-unknown` target, rustfmt and clippy, on the first build. `build.sh` maps the crates.io source paths out of the binary (`--remap-path-prefix`), so a build is byte-identical whichever directory and home it runs in.
- **wasm-bindgen-cli:** must match the `wasm-bindgen` version in `Cargo.lock` (`=0.2.130`, pinned in `Cargo.toml`); `build.sh` stops if it doesn't. Install it with `cargo install --locked wasm-bindgen-cli --version 0.2.130`.
- **wasm-opt** (binaryen), pinned in `build.sh` to version 133: `build.sh` runs `wasm-opt -O3` on the `.wasm` and stops if the version differs, because another version gives other bytes than the build CI deploys. Install the release tarball (`binaryen-version_133-x86_64-linux.tar.gz` from https://github.com/WebAssembly/binaryen/releases) and put its `bin/wasm-opt` on PATH; it is statically linked and needs no root.

## Build

```sh
wasm/build.sh
```

This writes:
- `js/wasm/employee_model.js` + `employee_model_bg.wasm` (`--target no-modules`), loaded by `js/employee-model.js` on the page and in the planner worker. They aren't in git (`.gitignore`): the `Site` workflow (`.github/workflows/site.yml`) builds them on every push to main and every pull request (cached on the sources and pins), runs `cargo test --lib`, and on main deploys that build with the site, so a change that fails to build or test never goes live. Without Rust, `wasm/fetch.sh` gets CI's build (below).

Node loads the same build through `wasm/node.cjs`: `require('./wasm/node.cjs')(js)` runs `js`'s glue as a function body, starts its `.wasm` with `initSync`, sets the global `wasm_bindgen` and returns a fresh `EmployeeModel` from `js`'s `employee-model.js` (default: this checkout's `js/`), so one process can load two checkouts. CI's smoke check (`.github/scripts/smoke-model.cjs`) starts the model this way. It isn't shipped.

Cache tags: the deploy stamps every `?v=` in `index.html` from the files' contents (`.github/scripts/stamp-tags.cjs`, run by `.github/scripts/assemble-site.sh`). `js/wasm/employee_model.js` and `js/employee-model.js` share one tag, a hash over the glue, the `.wasm` and the loader. The loader passes it on to the `.wasm`, and the page passes it to the planner workers as `model=`, beside the tags of the binding files (`traits=`, `core=`, `planner=`, `career=`). Nobody bumps a tag by hand, and the source's tags stay as they are, so a local preview needs the browser cache off (devtools' "Disable cache") to pick up a rebuild.

The build is reproducible: the same sources give the same bytes, here and in CI (remapped paths, pinned toolchain, wasm-bindgen and wasm-opt). Comments can change it too: an export's doc comment is the glue's JSDoc, and a file whose lines move changes the line numbers of its panic locations in the `.wasm`. Sizes after wasm-opt -O3: glue 77 KB (13 KB gzip), `.wasm` 933 KB (378 KB gzip).

`CFG.traitProductionPaid` is a runtime switch of the module (`setTraitProductionPaid`, set through `EmployeeModel.CFG.traitProductionPaid = true`), off as the game has it; turning it on clears the fresh-set tables that depend on it.

Unit tests for the pure Rust parts run on the host: `cargo test --lib` (from `wasm/`).

## Without Rust

```sh
wasm/fetch.sh
```

downloads the build CI made on main into `js/wasm/`: the `Site` workflow's `employee-model-wasm` artifact, which every run on main uploads and GitHub keeps for 90 days. It needs the GitHub CLI, logged in (`gh auth login`): artifact downloads need a login even from a public repository. The artifact lists the sources it was built from, each file with its blob id (the same list keys CI's build cache), and `fetch.sh` installs nothing if a file here differs, uncommitted changes included: build with `build.sh` then, or bring `wasm/` level with main. It only takes builds from runs on main of the repository itself, never a pull request's.

## Rules for code in here

- Format with `cargo fmt` (`rustfmt.toml`: the Google Rust style guide's settings that stable rustfmt has, with `use_small_heuristics = "Max"`); `build.sh` refuses unformatted sources. Keep `cargo clippy` clean.

Size:
- No `serde_json`, and no `Debug`/`format!` in code that ships: they multiply the module's size.
- Sort through `sort::sort_places` (indices) or `sort::sort_list` (any list): each `sort_by` instantiation costs ~4 KB of code.

The boundary (what the facades hand over and get back):
- Decode inputs once and call by handle, never per call: a `Snapshot`, a session, or a `Subject` (made by `EmployeeCore.subject(e, ctx)` in `js/employee-core.js`; pass it as `e` wherever the same employee and context are priced more than once). Long work runs in steps the facade calls (`Recommend`, `OutputOnlySearch`, `CareerRun`, `KeepSession.prepare`), so it keeps progress and cancel.
- An export's data inputs and results are `io::Js<T>`: the JS value whose shape the Rust type `T` decodes from (`decode()?` in the body, so a wrong shape is the export's error) or serializes to (`Js::new`), so the export list in lib.rs reads as the model's API. At run time it is a plain `JsValue`. An export takes one object per input, never a positional list of its fields; a result is a named object, never a flattened number array; and kinds cross by name (`{ kind: 'companyIds', place }`, a quote's `'reroll'`, a plan's `'swap'`), which the facades map to text. Options decode with their defaults in the module (`fresh::FreshSetOptions`, `planner::RecommendInput`, the price's budget), so the facades only pass them on.
- The rules' inputs (`model.rs`: `RulesEmployee`, `Context`, `Situation`, `Card`) are the plain objects the facade hands over, decoded once with `DEFAULT_EMPLOYEE`, `DEFAULT_CONTEXT` and `DEFAULT_SITUATION` applied: a number that is missing, null, NaN or infinite is unknown and takes the default (or is `None` where there is none), a value of the wrong kind is an input error, and each struct's doc lists its own checks. The rules read named fields and never see NaN from an input; the decode is the one place to change what an input means.
- A planner snapshot crosses once per call or session: the facade hands the plain object to `new Snapshot(s)` (`snapshot.rs`), which decodes it into typed records (`Company`, `Employee`, `Tool`; each employee and company also as the record the projection reads) and interns its strings (`project::intern`: 0 is undefined, 1 is `''`). The sessions (`Recommend`, `OutputOnlySearch`, `CardSession`, `RetentionSession`, `KeepSession`, `Career`) and one-shot calls (`evaluate`, `validate`, `uncertainty`, `quitRisks`, `observedMismatches`, `singleSwitches`) take the handle and build what they read from it in Rust (`planner::Plan`, `pricing::Roster`, the career's members). `withExclusions` and card pricing's horizon give derived handles (`exclude`, `withDays`). A snapshot changed in place is decoded again by the next call: nothing is cached per JS object. What an unknown number means is decided at the decode (snapshot.rs' module doc): one that only adds to something (management and the owner's Management bonus, toolbox value, training quota, engine output and bonus, a company's and its manager's bonus, a switch's cost, a tool's bonus, trait Production, Luck, Climber raise, the happiness a newcomer shares or income tax takes, saved days, a rarity's training value) is 0; one that may be unknown is `None` (the PP value, days to retirement, trainings left, potential, the game's reported figures and wage expectation, the happiness lost over the working life, storage, recruiting's values), hours since a move or a switch are infinite, and a timed event without its numbers is left out; the numbers `validate` requires (days, a company's margin, tax and capacity, an employee's stats, a tool's hours) are NaN, and every export that projects checks first that they are known where it plans (`check::numbers_known`: an input error, a card or retention price's failure; `observedMismatches` skips a company it can't rebuild), so the projection never reads one. So the hand-built test snapshots decode too.
- A callback (`price` in `cardPool`/`trainingOutlook`, `coworkers` in `freshSetValue`) is called through `rules::JsFn` with `catch`, so an exception it throws comes back as an `Err` instead of unwinding through the module. How many trainings ahead a rule looks (`depth`) is a finite number, else the facade's default for the call.

Inside the module:
- Numbers are plain `f64`. What an unknown or odd input means (its default, `None`, an input error) is decided where it is decoded, so the rules use `f64::max`/`min`, `round`, `total_cmp` and plain comparisons.
- A cache key is a typed value, or a structural hash, of what the cached value depends on; an approximation (a field left out on purpose) is named where the key is made, with the evidence. Employees, companies and tools go in snapshot order and ties break on it, never on id strings. A cache that lives across calls has a size chosen for the browser (`cache::Recent` keeps the most recently used entries); the reason is beside the constant.
- No libm function is used, so the host and wasm builds agree bit for bit. A fresh set's pick chances, each a difference of two near-equal powers, are summed directly (`fresh::best_of_chance`) instead of subtracting two `powf`s.
- A projection runs for a finite number of hours from 0. The exports check that at the edge (`planned_period` for a snapshot's period, `career::Model::new` for a working life), so the projection itself can't fail.
- A price given to the priced rules (`card_pool`, `training_outlook`, `second_wind_value`, `expected_training_value`) is `rules::Price::Given`, a closure that may fail: the JS callback (`rules::js_quote`, failing with what it throws), the career's pool (never failing: `Infallible`) or card pricing's Reroll (failing with its `Fail`, the projection budget). The rule stops at the failure and returns it (`Result<T, E>`). Each rule is one body behind a generic shell (`price_with`), not a copy per failure type.
- The projection (`project.rs`) reads flat records and runs in a workspace kept between calls, so nothing allocates per hour. Its result is typed and kept in the workspace, its lists reused between calls (`project::Projected`: the value, PP, the daily values, each member's totals, and for a re-tooled company the terms that reprice it, `Retooling`); readers take its fields. The order of its sums is part of the result (`instant`'s comments give it): a reordered sum can change the last bits, which `WASM_DIFF_STRICT=1` reports. Its hour rows are typed (`project::Row`); a part day past the last whole day, shorter than `EPS` days, counts in the last (`project::day_count`), which the planner's daily totals share.

## Layout

- `traits.rs`: trait ids, rules (the data half of the trait-table split) and the exclusive pairs. The display half (name, when, note) is `js/employee-traits.js`.
- `hourly.rs`: each trait's hourly effect, run by three passes (`rules::trait_value`, `ordinary_production`, `trait_output_today`) through the `HourlyEffects` trait.
- `rules.rs`: the EmployeeCore rules (wage, Luck odds, trait values, card outcomes and values, pools, outlooks, the game's card profit).
- `project.rs`: the planner's projection (`scene_of`, `effects`, `instant`, `profit_on`), on flat records with a reused workspace that keeps its result (`Projected`); snapshot.rs builds the records once, when the `Snapshot` handle decodes.
- `career.rs`: the career simulation (`EmployeeCareer.batch` and `careerOptions`). Career states are records (the projection's `EmployeeRecord` beside the rules' `RulesEmployee`), shifted and changed by card outcomes in the module and projected through `project::DirectProjector` (members the caller holds, no encoding). What states with one signature share (`State::signature`: a 64-bit structural hash of the days elapsed and every field a card changes, potential left aside as a measured approximation) is kept for the 100,000 most recently used signatures, and states with equal card pools share one, with each card's key (`card_key`) worked out once per pool. The hash runs every word through a full mixer: a plain xor-multiply let two states collide within 4,096 careers. The `Career` handle (`career::Model`) keeps its caches across batches; `CareerRun.step(n)` (`career::Batch`) runs n transitions, so the facade's generator keeps its chunking, progress and cancel.
- `pricing.rs`: card pricing (`cardSession`, the planner worker's `cards:begin`/`cards`) and retention (`retentionSession`). A session reads the `Snapshot` handle once (`Roster::new`: ids' places, tools, holders, saved days, the traits that change no projection); a price takes the subject's record with the numbers of `e` (the subject over the options, decoded with the defaults). It hands tools out with `handoffs.rs` and holds the local plan menu with its tool choices, the layouts (the subject as a gap), the projection cache (the 80,000 most recently used), quotes, `traitShift` and the screened menu; card variants are `EmployeeRecord` records changed by outcomes in the module, projected with `project::CallProjector`, and the pool's prices for Reroll come from `quote` itself (`Price::Given`, failing with its `Fail`). A projection is kept under its layout and the variant's key (the record fields a card can change). A state is a (subject, tools) pair: its plans and layouts are its own, its best plan, plan scores and screened menu are kept by the base variant's key (the subject with the price's numbers), and its quotes by the rules' inputs and the card, both compared by value. Plan descriptions and notes stay JS.
- `handoffs.rs`: tool handoffs, the timelines of a set of companies' members as free tools go round, for the planner and card pricing alike.
- `check.rs`: the planner's input checks (`validate`; its data checks, `data_problems`, are also what `numbers_known` asks before anything is projected), who it can't reproduce (`uncertainty`) and who may quit (`riskWarnings`' rule). The decode keeps the facts they read about the values as they came (`Number.isFinite`/`isInteger` don't convert); results are kinds and places, the facade has the text.
- `planner.rs`: the planner (`evaluate`, `recommend` with its output-only comparison, `withExclusions`' stat check). `Plan::new` reads the `Snapshot` handle; `Env` is it as a plan sees it (each place's company now, re-tooled ones included) with the projector: its cache, the class repricing of re-tooled companies, and the counters the budget reads. `Search` is `recommend`'s best-improvement loop, one round per `step()`, so the facade keeps `onProgress`. Projection keys are words (a tool held from hour 0 keys like a timeline starting at 0, which is the same projection); a candidate's key is the change by places and tool classes (`CandidateKey`), which the report gives the facade to write as text. Ties between candidates go to the earlier one. After the search, `output_only` searches again for output alone with the projections left and scores that plan with the full model (`Recommend.outputOnly()`). The page makes that comparison alongside the search, in a second worker (`OutputOnlySearch`, a `Comparison`): it starts with the most projections the search can leave and, given the search's terms (`Recommend.outputOnlyTerms()`), keeps to the budget actually left, starting again only if it has already projected past it. Projections only grow and the budget is read only at each candidate's check, so the result is the one `outputOnly()` gives. Notes, warnings' text and names stay JS.
- `switch.rs`: product switching (the planner's `priceSets`, `retool`, `switchContext`, `singleSwitches` and `evaluateRetooled`), with the game's switching rules in its docs: the price sets, a company re-tooled onto a good, the goods to try, and Top Products' single switches, which re-tool each company where it stands (`InPlace`: saved days on the good, tools that don't fit off), as `evaluateRetooled` does for one good. The regional bonus stays the page's `computeProductionBonus`; the facade hands its results over per company and good.
- `sort.rs`: the stable sorts, through one `dyn` comparator (`sort_places`, `sort_list`): a `sort_by` per closure costs ~4 KB of code each.
- `fresh.rs`: recruiting (`candidateValue`, `freshSetValue`, the newcomer's own tables).
- `keep.rs`: the keep step and recruiting over a snapshot (`KeepSession`, `EmployeePlanner.keepSession`): each employee's model and context in any roster of their company (all of it or all but one), in their company as it is with each coworker as a model in their own context (`model`: the Training page's calculator, card jobs, training outlooks and energy curve read these), and a company seen by a newcomer joining it (`joinSetup`). It prices keep rows (retention from pricing.rs, the potential's trainings, a fresh set in the company without them, built ahead a step at a time by `prepare`), fresh sets with the coworkers' side read natively, what a newcomer does to the coworkers' traits and a typed candidate. Per roster it keeps the coworkers' trait values, each newcomer's impact and fresh sets by `alt` and slots; the newcomer's own tables are fresh.rs' cache. The page keeps the verdicts, sorting and text.
- `cards.rs`, `cfg.rs`: the card tables and game constants. `snapshot.rs`: the planner snapshot, decoded once per call or session into typed records. `out.rs`: the rules' result shapes. `io.rs`: `Js<T>` and the serializer's settings. `lib.rs`: the exports.
